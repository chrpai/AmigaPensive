Nuker
=====

  for the nuker to be able to update filelists correctly it needs exclusive
  access to the filelists.

  my idea is thus:  when the file lists are not in use, rename them and
  set a flag somewhere in hbbs (to be defined) to indicate the filelists
  are in use.  (somewhere in the conference structure would be best)

  then process the files

  then rename them back and unset the flags.

  2nd option..

    define flags
    COPY file lists.
    process files
    copy file list back over the old ones.
    unset flags

      Nope, if something is reading a file list it ain't gonna like it.

  now a seperate task would do all the above.  And you would have another
  program that the sysop/co-sysop uses from the bbs prompt that sends
  the requests to the nuker processor.

  check for a port called HBBSNUKER, if the port doesn't exist, fire up the
  nuker processor, then wait for the port to appear, then send the nuke
  details to that named port.  but only wait a short time for the port to
  appear. e.g.

  user types NUKE at bbs prompt

  NUKE door looks for HBBSNUKER port, starts the nuker.

  NUKE waits 10 secs for HBBSNUKER to appear, checking every .5 second

  if HBBSNUKER does not appear exit NUKE with message "Nuker Not Availiable"

  ask user NUKE details (filenames, confs, award, remove, kill, rename etc..)

  check port HBBSNUKER still exists

  send details to port

  exit NUKE with message "Nuke request being processed"



  HBBSNUKER then gets the info, waits until it can safely rename the filelists
  then processes pending requests and exits.

  HBBSNUKER could also remain in memory so that it doesn't have to be fired
  up each time a nuke is requested.  but that would lead to longer
  reboot/startup times...

  control will also have to be made aware of the nuker and should be told
  not to exit because the nuker may be running.  (library open count must be stored
  in BBSGlobal.)

Ideas
=====

  Kewl, have an IRC BOT node! this would be difficult to implement for doors using check
  raw and the like..  my ideas is you can /msg Hydra^CP BBSLogin or something, then instead
  of telnetting to the bbs you can do everything in a private DCC message window of your favorite
  IRC client, x-fers would be done by XDCC or something..

  call <Name>_Door_<n>  <name>_Data_<n> to avoids confusion when using
  something like SCREEN or ECHO for a door type.

  add options for /X help for sysop's and users to help them change between systems
  (i.e. when a sysop presses F10 wanting to log a user off tell him to press
  SHIFT+F10 instead of just F10..etc... do the same sort of things for door commands..)

  Add option "SkipOK" to Device config so that if you have a weird modem you
  can tell the bbs not to wait for the OK string after commands..

  add timeout on doors,  best place would be where NODE looks at messages coming
  from the door program,  you could set a timer when the door has started (when you get
  a doorstart IO message) and see if it times out, if it does then cancel running that
  door.  Also you'd have to reset the timer everytime the node received a message
  from the door,  BUT, file transfers will be sending all their data via messages
  so you could only reset the timer on bog standard messages,  perhaps set up a new
  type of message for use only by transfer protocols that would be skipped...

  have a button in the node's settings window to manually stop a door.  This is cool
  if a door has crashed and you want the system to continue..  also the timeout on the
  door function would need to call the same cleanup function.  was thinking of being
  able to pass the node a pointer to the door function that does the cleanup for the
  door at door startup time, then anytime after anything can call
  HBBS_CleanupDoor(N_ND->ActiveDoor) to stop the door. (or something similar)

  have option for sysop, so that they can choose to strip all ansi colour changes
  from the watch window, thus speeding up the user's display. (this would also be better
  if the sysop was using watch windows on a 2,4 or 8 colour screen.)

  Network mail!

  modem inactivity reset,  let the modem reset itself if no-one calls the bbs
  for a certain duration or there are a set number of invalid/misconnects..

  have somewhat versatile login times, so you can specify what days a user is allowed
  to logon and between what times and how many calls they are allowed for each day
  etc etc..
