Chapter 8 - FidoNet

Introduction

This part of the manual covers the use of the message processing tools supplied with Zeus such as ZMP (fidonet mail import and export utility), ZMailer (fidonet packet transfering utility) and nodelisting documentation such as creating your own point net and using Traplist for parsing nodelists. Nodelists are like a telephone book listing the names and numbers of all the systems connected to FidoNet.

Also covered are other mail applicable aspects such as file hatching with fidonet technology.

About Fidonet and other Networks.

FidoNet is the largest amateur network in the world. It was started in 1984 by Tom Jennings. Currently more than 20000 nodes worldwide are connected. The network has a hierarchic tree (or star) topology:



Zones are divided in Regions, which are divided in Nets. The Nets consist of Nodes, which are usually (but not necessarily) Bulletin Board Systems. Each node has a unique address which consists of four parts: Zone, Net, Node and Point, in text form expressed as "zone:net/node.point". Zone numbers 1 up to and including 6 are used by FidoNet: 

    1 = North America (United States of America and Canada)
    2 = Europe and Commonwealth of Independent States
    3 = Oceania (Australia and New Zealand)
    4 = Latin America
    5 = Africa
    6 = Asia


There are several other networks that use FidoNet Technology. Networks such as AmigaNet use higher zone numbers which are allocated by a central body, 39-41 for example.

Many nodes have one or more points. A point is a user who gets mail from a node (it's "boss"), usually as compressed mail files. This way they can read and write messages offline saving time and money. The point address of the boss is 0 (e.g. 2:441/58.0) but the ".0" is often omitted from the address.

To operate successfully as a FidoNet node a variety of tools are needed. As you would expect Zeus provides these tools built-in but also has extensive support for third-party programs.


Mailer (also known as a FrontDoor)

The mailer is a program that waits for incoming calls from users and FidoNet systems. Users calling are passed through to the BBS. FidoNet calls are intercepted and a handshaking procedure is started. This handshaking establishes a common protocol between the two mailers, exchanges information about each other's system and makes sure that the connection is secure (i.e. the passwords match and mail is not being received by a foreign source).

Zeus's internal mailer is called ZMailer and is stored in Zeus:Bin. Its configuration program is Zeus:Prefs/Mailer.

Other Amiga mailers are available and compatible with Zeus. They are all available on the AmiNet.

Mail Processor (also known as a tosser, scanner or packer)

This program is used to "import" and "export" mail. Most mail processors work on a two phase basis. Exporting scans the message bases on the BBS searching for mail that has not been seen by all the systems who take an area (or 'echo') and gathers it into "bundles" stored in the "outbound" directory ready for collecting or sending by the Mailer. Importing scans the "inbound" directory for new mail bundles received by the Mailer and unpacks them into the message bases ready for reading by the BBS users and the system's points.

Zeus's internal mail processor is called ZMP and is stored in Zeus:Bin. Its configuration is stored and changed using a text file called Zeus:Config/ZMP.cfg.

Other Amiga mail processors are available and compatible with Zeus (using the mbstarmsg.library, see chapter Message Subsystem, section Message Base Libraries).

Tick Processor

FidoNet also provides support for "file echoes". These are similar in setup to a message echo, except they carry binary files rather than ASCII message text. A tick processor reads in TIC files from the inbound directory and adds their associated files to the correct file areas. Tick often has a companion called "Hatch" which allows FidoNet systems to send files to the file echo for distribution.

Zeus's Tick processor is built into the Zeus Mail Processor (ZMP) and can be run by specifying the TICK keyword on operation.

Other Tick processors for the Amiga are available, but not recommended for use as they cannot integrate with the Zeus file catalogue which renders them only partially useful. It is still possible to use them if they set the file comment/note of the file, in which case files can be added to the Zeus file catalogue by running "FileManager AddNew FileNote Areas <areas>".


Areafix

Areafix is a relatively new FidoNet utility designed to take the pain out of running a busy node system for the SysOp. Before Areafix was used FidoNet administrators had to "fix" people into message echoes manually by editing their configurations. This was time wasting when users wished to add a large number of echoes. In addition to this, Areafix allows user's to connect to echoes not taken by the node. This is done by sending a chain of Areafix requests back up the FidoNet hierachy until a system is found which taks the echo that the user requries. Areafix could cause huge space wastage and gigantic mail packets if abused, so most Areafix programs allow strict access restriction systems to be implemented to stop some systems fixing into private echoes, too many, or any at all.

Zeus's Areafix is built into the Zeus Mail Processor (ZMP) and is automatically run when an import is in progress.


Nodelists

To function in a proper environment the Zeus specific mailer (ZMailer) requires you to have configured nodelists for every FidoNet technology network you carry on your bulletin board. This may include a pointlist, as nodelists only carry information about zones, networks and nodes.

The 'TrapList' utilities you will need to compile and update nodelists can be found on disk #4 of the Zeus distribution set as `NODELIST.LHA'.

Please take the time to read the relevant documentation for traplist and the nodelist tools within that archive for a more verbose description of nodelist technology than covered here.

To cover briefly setting a system up for a link with your BBS system then it's just a matter of using the SetPasswd tool within the Nodelist archive like this:

SetPassWd <Session Password> Address_1 Address_2 etc....

These passwords can also be set within the traplist configuration file which will be explained later on, along with an example configuration file. This is also the recommended route since the nodelist data can be damaged and lose all the password information, and you can backup the traplist configuration file very easily.

Needless to say both you, and the system(s) you are exchanging mail with will have to use the same passwords, else the link will be considered insecure and mail will not be transferred.

Here is an example traplist configuration which will give you an idea on setting up to recieve the Zeus support echos. 

ZONE 85

NODELISTPATH "NODELIST:"
BUFFERSIZE 65536
REPORT "Ram:Traplist.log"
NOCHECKCRC
NODELIST "ZeusNet"
PASSWORD "SECRET" 85:1/1.0
DIAL "44" "0"


The entries broken down individually are :-

Zone - This is the network number. 85 is a unique number used by the ZeusNet. While more than one nodelist can be parsed with this single config file, you must use only one Zone line which should be the lowest network number you are on.

NodelistPath - This is the directory where the nodelists and nodediff files are present. You must assign Nodelist: to a directory and use that path here as in the example above.

BufferSize - The bigger the buffer, the quicker traplist can process the nodelists. Obviously this depends on memory restrictions with your computer.

Report - Path to a file to output any messages from the processing. A logfile you can refer to to check if it all worked okay.

NoCheckCRC - If this line is ommited then Traplist will run a crc check on the nodelists listed in the following lines and compare it to the number within the nodelist itself. This is really only of use to sysops using nodediff files for updating nodelists and for nets as small as Zeus, it's easier to just release the full nodelist and so crc checksums within the nodelist are rarely needed.

Nodelist - As many of these entries as you like can be configured. Each name will be checked by traplist for a nodelist <name>.082 for example and processing will take place if it finds a valid file. You don't need to specify an extension number on the name as traplist will do it for you, and automatically makes sure it uses the highest number.

For example if ZeusNet.024 and ZeusNet.046 were found, *.046 would be processed.

Password - This is how you configure session password between systems linked to your bbs for security checks and to prevent any system polling your Mailer with the right address and stealing someone elses mail.

For example

PASSWORD "Backyard" 85:1/13.0

This means that if system 85:1/13.0 calls your mailer then no files will be transferred unless it also sent a session password of Backyard.

DIAL - This is a modifier string for changing phone number formats within the nodelists as they are processed.

For example

DIAL "44" "0"

means any instances of 44 at the start of a phone number for a system in the nodelist would be replaced with 0, used by UK sysops as the 44 is the international dialling code used to dial into the the UK from outside. A system with the number "44-1423-123456" in their nodelist entry would be replaced with "01423-123456" when dialling out. You should check what your county's international dialling code is (you can find examples in the nodelist) and replace it for the 44 here.

Here is an example pointlist file which you can customise to generate a list of points from which ZMailer will get their system information when a call is recieved from their address. It's not actually necessary to use a pointlist with Zeus but you will still need a password line for each point listing their session password and addresses or they will not be able to send or recieve mail. You set up a points password details within the TrapList config file (as detailed above) as normal, or with the SetPasswd tool within the Trapdoor archive. Setting passwords in the TrapList configuration is recommended as passwords set with SetPasswd can easily be lost if your compiled NodeList becomes corrupt. 

;A My Pointlist/Fakenet list -- fake crc 0 : 0<Ctrl M>
;A^M
Zone,2,->^M
Region,254,->^M
,255,BackYard,North_Harrow,Anthony_Brice,44-0-181-1234567,9600,HST,MO^M
Point,1,Hell_On_Earth,North_Harrow,Anthony_Brice,UNLISTED,9600,MO^M
Point,3,The_Garage,Rayners_Lane,Gary_Pearse,UNLISTED,9600,MO^M
^Z


Note: The information within the < > brackets are control codes which need to be used when generating your own pointlist. <Ctrl M> means press Control and M at that point. I recommend using an editor such as CygnusEd when creating a nodelist, as that allows the insertion of such control codes, and nodelists MUST have these codes to process properly.

The Point lines are defined as below:

Point,<PointNumber>,<SiteText>,<Location>,<Point Name>,<PhoneNumber>,<Baud>,<Flags>


PointNumber - Their unique number as a point.

Site Name - Some text describing their system.

Location - Their town / state.

Phone number - Can be set to UNLISTED as above, which means you can't use a mailer to dial them up by using their fido address as they are points and wouldn't have a mailer to answer the phone.

Baud - A maximum rate of 9600 due to some old nodelist processors not handling handle a five digit number.

Flags - Usually set to MO (Mail Only).

Explanation of configuration tags.

MSGBUFFER <bytes>

defines the largest FTN message ZMP will be able to import. <Number> is the amount of bytes ZMP allocates and must be a minimum of 32768 bytes.

IDXSTORE <records>

defines the amount of index records in ZMP.index. The more indexes, the better the dupe checking and reply linking but ZMP will use more memory, disk space and time. Each index record is 36 bytes long.

CRCDUPE

if a message has no `ID' with which to uniquely identify it, ZMP will check if the message is a dupe by ensuring no two messages have exactly the same header (to, from, subject, date, etc.). It is remotely possible for two messages to have the exact same header, however this isn't very common.

NODUPECHECK

disables Dupe checking completely.

FLOCTRL

makes ZMP use special characters in the .?LO flow files. Most Amiga mailers support this flag (including ZMailer), but some older ones may require NOFLOCTRL to be set.

4DFLO

makes ZMP use 4 dimensional filenames in the Outbound directories. Again most Amiga mailers (including ZMailer) support this format.

CTRLCHAR <character>

indicates that mail packet files should be prefixed with <character> in outgoing mail packets. The default is a ^ which means that the file should be deleted. Most Amiga mailers support these characters. Other acceptable values are:

# - Truncate this file to zero length

^ - Delete this file (with logging)

- - Delete this file (without logging)

~ - Don't send this file

NOCHKNETDOMAIN

When a netmail's origin and destination addresses are not in the same domain, ZMP will attempt to bounce the message back to the sender. Specifying this keyword disables this checking.

NOCHKPKTDOMAIN

If ZMP detects that a message packet's origin and destination addresses are not in the same domain, it will rename it *.BAD and not process it. Specifying this keyword disables this check.

BOUNCEBADADDR

If you use netmail domain checking (by not specifying NOCHKNETDOMAIN in your config) then badly addressed messages will be bounced back to the node which sent them (if possible).

BOUNCENOROUTE

If a netmail is processed which is not destined for your system but ZMP is unable to route the message to another system, a message will be sent back to the sender telling them about it.

BOUNCENOUSER

Specifying this keyword causes ZMP to check the To: field of every netmail that is destined for your system against your current list of users. If the recipient does not have a user record, ZMP will bounce the message with the message 'User not known at this address'.

UNPACKDIR <directory>

The temporary directory ZMP will unpack mail bundles into. Specifying a directory in the Ram Disk (RAM:) will make importing quicker, but will cause problems if trying to import large sized message packets on a system without much free memory.

PACKDIR <directory>

The temporary directory ZMP will pack the mail bundles from before they are put in the outbound directory. The same limitations apply here as with UNPACKDIR.

ATTACHDIR <directory>

The directory to place any files that arrive attached to messages. If you do not use this keyword, the inbound directory will be used.


Also..

INBOUND <directory>
OUTBOUND <directory>

These force ZMP to use different directories than those set in the General Paths configuration (in the Prefs/System program). Useful if you don't want ZMP to import packets/bundles received via ZMailer (if you use another message processor such as MailManager), but do still want ZMP for other work.



Each network you have is defined under a NODE entry

NODE <network address>

NODE defines your address in a FTN network. The address must be at least 4d (Zone:Net/Node.Point) and preferably 5d (Zone:Net/Node.Point@Domain).

AKA <network address>

Defines one or more AKA ("also known as") addresses. These extra addresses allow you to, for example, run a multi-node system with each node having its own network address. Mail can then be sent to any of your addresses and still be correctly processed without the need for additional, complete, NODE entries.

POINTNET <number>

The net number defined by POINTNET will be stripped out of incoming messages and replaced with 3d control lines.

ZONES <zone number, zone number [...]>

Defines all valid zone numbers for this domain. These are used when incoming netmail messages have no domain information. A maximum of twenty may be defined.

CREATENEW <area>

When an echomail comes in with an unknown tag and the sending system has ALLOWNEW capabilities, ZMP will also create a message area on your board. If the given message base number is already used, ZMP will increment it until it finds an unused one.

CREATELINK <area>

If you want to link into a pass-through area you would usually have to create the area on the board and then add your address to the appropriate AREA line. By specifying this keyword (BEFORE your AREA lines) you only need to add your address to the AREA line and ZMP will create a new area on the board while it loads its config.

The Message Base Number works in the same way as CREATENEW.


Under each NODE (network) entry, you then list your SYSTEMs - those nodes and points with which you will be sharing mail.

SYSTEM <address> <flag array> <archiver> <packet password> <areafix password> <tick pw> <groups>

defines a known system for the current network. The arguments are as follows:

Address - The FTN address of this system.

Flag Array - Nine characters together (i.e. 'U2YYNNNBY') as follows:

1. AreaFix Access - One of the following characters:

N No AreaFix access. All requests from this system will be ignored.
Y May use %LIST, %QUERY, %UNLINKED, %HELP, %PAUSE, %RESUME, %RESCAN, %FORCERESCAN and link/unlink into echos.
U As for 'Y' but AreaFix enables uplink requests. (See AreaFix section).
C Full AreaFix control. May create, delete and rename echos. May also request for other systems.

2. Control Type
Specifies the number of dimensions used on SEEN-BY and PATH lines. Type 2 must only be used if the calling point needs to use a "pointnet", this is only necessary if they use extremely old software.

2 Net/Node for nodes. PointNet/Point for points.
3 Net/Node for nodes. Net/Node.Point for points.

3. Packet Change
Specify 'Y' to make ZMP generate the same packet header types for this system
as it receives. 'N' to disable.

4. Archiver
Change Specify 'Y' to make ZMP change the archiver it uses on this systems mail
packets to match the ones it receives. 'N' to disable.

5. Netmail Flow
Specifies the 'flavour' of netmail packets. This is how the messages will be sent by the FidoNet mailer. The changes are visible in the Outbound mail directory as <address>.FLO, <address>.HLO, etc.

N Normal - You must call the destination to deliver.
H Hold - The destination must call you to deliver.
D Direct - Mail will be sent directly to the SYSTEM in question.
C Crash - All netmail will be 'crashed' - it will be sent directly to the SYSTEM in question via a direct call, even if there is a routing entry which affects this address.

6. Echomail Flow
Specifies the 'flavour' of echomail packets. Same options as the netmail flow
flag.

7. Tick FLO
Specifies the 'flavour' of *.TIC files. Same options as the netmail flow flag.

8. Packet header
Specifies the packet header type used on outgoing mail packets. May be one of:

A Basic FTS-0001 revision 15 header. No point information - not a recommended format.
B FSC-0039 header. Uses four dimensional addressing.
C FSC-0048 header. Uses four dimensional addressing. Some programs cannot use this format, but it is slightly more advanced. At least some Xenolink versions require FSC-0039 and will reject these.
D FSC-0045 (Packet 2.2) header. Has full five dimensional addresses.

9. Archive Netmail.
If this SYSTEM can handle archived netmail, set this flag to 'Y', otherwise set to 'N' and the netmails will be delivered as an uncompressed PKT file. Often, Amiga programs can handle compressed netmail while PC ones cannot.


Archiver

The name of an archiver as defined with Zeus:Prefs/Archivers. All echomail (and optionally netmail) for this system will be archived using the specified type.

Packet Password

For extra security, you can specify a password which will be placed in the packet header. If you do not want to use a packet password (or the system does not support them) use '-NONE-' without the quotes.

AreaFix Password

If the system has AreaFix access then you can specify a password which the system must put in the subject field of all AreaFix requests. If you don't want to use an AreaFix password then specify '-NONE-'. If you want to use the packet password for AreaFix as well, specify two quote marks like "".

Tick Password

The password to be used in *.TIC files sent and received to/from this system. You can disable the password by specifying '-NONE-', you can duplicate the AreaFix password by using "".

Group Number(s)

The area group numbers that this system has access to. AreaFix uses this information when deciding what echoes this system can link into. You can place more than one group number here, simply put a space between each one and ZMP will recognise them all. Learn more about groups below, in the AREA section.



After having defined which SYSTEMs are in this network, we can now define the AREAs which are available to them.

AREA <tagname> <group> <address address [...]>

This keyword defines an echomail area. The arguments are:

TagName

The tagname for the echo.

Group

A number between 0-65535. By grouping certain echos together you can easily restrict access for a system. Each AREA can belong to one group (NB: please don't confuse ZMP groups with Special Interest Group on the BBS) and each SYSTEM can belong to more than one group. For a SYSTEM to be allowed access to an AREA via AreaFix, the SYSTEM must belong to the group of which the AREA is a member.

Linked Systems

A list of system addresses which are linked into this echo. If you do not specify your address, the messages will not be stored in any message base on your BBS, but be 'passed through' to the other connected systems. This PassThough option is used when you don't wish to read an AREA for yourself (or your BBS users) but you do allow other people who area Linked to the AREA to be able to still receive it. Note: if no other SYSTEMs are linked to the AREA, imported messages are simply deleted on import. Therefore you should watch these areas and disconnect from your uplink when nobody else is linked in.
The address may be prefixed (i.e. =12/3 #15:44/123) with one of the following characters:

'-' The system has read-only access to this echo.

'=' The system is not linked in but if they link in using AreaFix, they will have read-only access.

'|' The system is linked in but their feed is currently paused (using the %PAUSE AreaFix command). On issuing the %RESUME command, they will have normal access.

'#' The system is linked in but their feed is paused and when they resume the area, they will have read-only access.

Advanced usage:

If your BBS is a hub or other distribution system in a network, you may have several AKA addresses in addition to the main NODE address. While ZMP will import messages addressed to an AKA without problems, it is not immediately possible to export messages using these AKAs. To make this possible, there is a special command which can be embedded inside the list of linked addresses of an AREA or TICK (see below) line.

Take this fragment of ZMP.cfg as an example:

NODE 2:442/107.0
AKA 2:442/110.0

AREA AMIGA_UK 0 .1 .2 .3 USEAKA 2:442/110 .4 .5

Downlink .1, .2, .3 AND .5 receive Fido from 2:442/107. Point 4, however, receives Fido mail from the AKA 2:442/110. Noteworthy points: any system linking in via AreaFix automatically receives mail from the NODE (main) address and netmails always come from the NODE address.

The `scope' of UseAKA is therefore only one address - only the next one listed (here, .4) is exported to as 2:442/110. The next after that, .5, is exported to as normal using the NODE address, 2:442/107.


After defining the AREAs, we must provide one or more ROUTE lines in order that ZMP knows where to send Netmails written or received.

ROUTE <from address> <to address>

Specifies Netmail routing information. When Netmail's are imported to the system, their to address is compared against the "from address" entry of each ROUTE statement in the applicable network. If a route statement matches, then the Netmail will be routed to the "to address", e.g., if a netmail addressed to 2:888/67.0 was imported to the system and the following ROUTE lines existed: 

ROUTE 40      56
ROUTE *:*/*.* 1


The first entry would be ignored as the to node of the message is 67, not 40. The next entry is a wildcard and all addresses will match it. Therefore the message would be routed to node 1 (2:888/1.0).



There are more configuration options which ZMP can use in each NODE section. The following keywords must appear after a NODE definition (preferably, after the ROUTE lines):

NEWTICKAREA <File Area Number>

When ZMP creates a new TICK area, it uses the given number as the file area for the new TICK line. ZMP does NOT create new file areas on your BBS.

TICK <TagName> <Group> <File Area> [Linked System Addresses]

Defines a TICK file echo. The format and usage is the same as the AREA line but you need to specify a file area number so ZMP knows where to save the files. If you wish to have a pass-through area, set the <File Area> to zero. "UseAKA", as demonstrated in the AREA documentation above, is equally valid in the TICK lines.

FILEECHO <TagName> <FileAreaNumber>

Echomail messages may also have file attaches. This keyword links an echo tag to a file area on your BBS. Files that come attached to messages in <TagName> will be uploaded to area <FileAreaNumber>automatically.

UPLINK <Address> <Password>

Specifies an uplink address for AreaFix to automatically request known areas. See AreaFix section for more information. The password should be the one you use when accessing the given systems AreaFix.

ALLOWNEW <Address> [Address...]

When a message is received with an unknown tag ZMP will create the AREA in your ZMP.cfg only if the message came from an address defined with the ALLOWNEW keyword.

AUTOECHOADD <Address> [Address] ...

Whenever ZMP creates a new AREA, it automatically adds the addresses specified with this keyword to the export to list. Very useful if you are a hub for a small network!

AUTOTICKADD <Address> [Address] ...

Whenever ZMP creates a new TICK, it automatically adds the addresses specified with this keyword to the export to list.

TWITUSER <User Name>

Any messages being imported that are from <User Name> will be deleted.

TWITADDR <Address>

Any messages being imported that are addressed from <Address> will be deleted. <Address> may include wildcards.

MAXPKTSIZE <Bytes> <Address> [Address] ...

Some systems cannot handle mail packets over a certain size. This keyword specifies the maximum number of bytes per packet to create for the listed systems (wildcards accepted).

MAXBUNDLESIZE <Bytes> <Address> [Address] ...

More importantly, some systems cannot handle mail bundles (archived packets) over a certain size, usually due to memory or disk limitations. This keyword specifies the maximum number of bytes per bundle to create for the listed systems (wildcards accepted). Remember that as the packets are compressed to about a third of their usual size, so if MAXPKTSIZE is set at 256000 bytes, MAXBUNDLESIZE at 512000 is plenty!



Here are two special commands which can appear during the AREA lines:

ITRANSLATION <Table1> [Table2]

Translation tables are stored in Zeus:Config/Translation. On import, the text is translated through <Table1> and then, if specified, through <Table2>. The convert the character set of messages from one type to another. Defined tables affect all areas after the keywords, e.g. 

ITRANSLATION ISO IBM
OTRANSLATION IBM ISO

AREA ...
AREA ...

These areas are affected by the ISO-IBM translations.

ITRANSLATION SE7 ISO
OTRANSLATION ISO SE7

AREA ...
AREA...

These areas are affected by the SE7-ISO translation tables.


OTRANSLATION <Table1> [Table2]

On export, the text is translated through <Table1> and then, if specified, through <Table2>. It is then exported to all connected nodes.
The translation tables can be found as seperate files in the directory Zeus:Config/Translation/



Other ZMP configuration tags.

These are some very useful (sometimes necessary) configuration options which should appear at the top of the ZMP.cfg file, before any NODE sections.


DELFILECHAR <Character>

This character will be prefixed to netmail attached files in the destinations .FLO file if you have turned on FLOCTRL and DELNETATTACHED.

DELNETATTACHED

When an incoming netmail, which has attached files, is not destined for your system the files will be added to the destinations FLO file with the DELFILECHAR prefixed to the file name so your mailer will deleted the file once sent. This only works in conjunction with the FLOCTRL keyword.

DELNETMAIL

ZMP always imports netmails into your message base but if this keyword is used, ones that are not from or to your system will be deleted during export.

ATTACHDIR <Directory>

Files that come in attached to messages will be put in the ATTACHDIR. When the messages are exported, ZMP will look here for attached files.

AREAFMT <Format String>

When AreaFix adds a new area to your ZMP.cfg it uses the specified format string to make it match to your other AREA lines. You need one '%s' (for the tagname) and one '%lu' for the group number. Both are standard C formatting codes. There are two other special codes which are: 

       \t  Tab (single backslash followed by t)
       \s  Space (single backslash followed by s)


TICKFMT <Format String>

As for AREAFMT but this specifies the format of TICK lines. You need an extra '%lu' in the format for the file area number, but apart from that, it is the same as AREAFMT.

NOAREAFIX

Disables ZMP's internal AreaFix. Should you use ZMP on a point or use a 3rd party AreaFix program, set this to completely disable AreaFix in ZMP.

MINMSGS <Number>

Specifies the number of new messages that must be in a message base before ZMP will try to export the area. By running ZMP with the arguments `EXPORT FORCE', ZMP will ignore the MINMSGS setting. You should run ZMP with FORCE at least once a day (on a Cron) and after major mail polls in order that messages in low-flow areas are not left unexported for days or weeks.
The purpose of this option is to assist those SysOps running a busy system on a slower computer. If you had to pack messages into 50 downlink bundles every time a point delivered their mail, you could be waiting for a long time with a 68000 or 68020. Using this, you can accumulate single posted messages over several calls until there is enough to make the export `session' worthwhile.

NOUSERBOUNCE <User Name>

If you have user bouncing enabled (with BOUNCENOUSER - don't get confused!) there are some names that you might not want to cause a bounce with, i.e.'SysOp'. This keyword gives you this option. One name per entry, but as many entries as you wish.

NETEXEC <Name> <Password> <Executable>

If a netmail is received addressed to <Name> the given executable will be run. <Name> must have quotes around it if there are spaces.

Password should be a maximum of ten characters long but may be pecified as '-NONE-' which will disable the password checking. Using NETEXEC before any NODE statements defines a global entry, you can also limit the entry to a single network by putting it after the appropriate NODE entry.

Various control codes can be passed to the "Executable" line of NETEXEC to expand into data relating to the message:

%f
Who the message is from

%t
Who the message is to

%s
The subject of the message (Usually password but could be other data if your password is -NONE-!)

%A
The from address of the message (Zone:Net/Node.Point)

%D
The dest address of the message (Zone:Net/Node.Point)

%n
The number of the saved message

%a
The area the message was saved into

%F
Who the message is from (with underscores)

%T
Who the message is to (with underscores)

%S
The subject of the message (with underscores)

%%
A '%' character

DELBADMSGID

If a message comes in with a non-FTN standard MSGID kludge it will usually be imported. Specify this flag if you want these messages to be deleted during import. Not really recommended, as there are a lot of PC packages which really mess it up, and gated Internet messages often don't use FTN style MSGID lines.

ALLOWRESCAN

By specifying this keyword, you allow systems that have AreaFix access to use the %RESCAN and %FORCERESCAN commands. See the AreaFix help documentation for more information.

ALLOWMIXEDPKT

Special kludge which causes echomail packets to be processed in a slightly different way to support some brain-dead PC tosser software!

NOECHOCREATE

Disables ZMP's auto echomail creation function.

NOTICKCREATE

Disables ZMP's auto tick area creation function.

TWITUSER <User Name>

Any messages being imported that come from <User Name> will be deleted. This can be a global setting for all domains, but can also be restricted to a single network by placing in a NODE section. Don't worry about this breaking FidoNet's golden rule of not interfering with in transit mail - mail from twits will still be passed on to linked SYSTEM's or routed in netmail. You'll just never see it on your BBS.

HIDEARCS

When (de)archiving mail packets, the archivers output will be redirected to NIL: if this keyword is set.

ANNOUNCEAREA <Message Area Number>

When a new Message or Tick echo is created automatically, a message will be posted in this message area to inform yourself and/or your users. Placed in the global section, this will affect all areas. In the NODE section, it will affect only that network. You can, of course, also have a global entry and still have messages for some networks go to unique areas by placing an ANNOUNCEAREA in any NODE section.

NORETRECREQ

From Zeus version 1.2, ZMP can send "Receipts". These are messages sent to a user when their message reaches your system and is addressed to a user here: think of them as confirmation that a message has got to it's destination. Programs such as Spot and MailManager can request these be sent, and in any case a receipt will only be sent if requested by whoever sent the message. This switch stops ZMP sending receipts for received netmail.

NOAUDITREQ

Also from Zeus version 1.2, ZMP can send "Audits". These are messages sent to a user when their message reaches your system and NOT is addressed to a user here - the audit message sent to the original sender tells them where the message was routed to after passing through your system. They can be thought of as being like the PATH: or Via lines which is are every message, only in this case Audit trails can be used to check where a message is failing to be correctly routed on from. This switch stops ZMP sending audits for received netmail.

NOAREAFIXFUZZY

Disable fuzzy string matching on incorrect Areafix echo requests (where an echo specified doesn't exist). This is on by default.

QUICKDISPLAY

Updates the display in the shell every second rather than for every message.



Uplinks

Uplinks are systems which you poll for mail, have a wider range of echos, and you have AreaFix access to.

To setup an uplink, you need to specify them in the config with a SYSTEM line and an UPLINK line. You also need a list of echo tagnames that they carry and you have access to. This list needs to be saved in the Zeus:Config/AreaFix/ directory and the filename format is z.n.n.p.LST

An example:

I have an uplink at 1:234/56.0 and they carry three echos which I don't. Their names are ECHO1, ECHO2 and ECHO3. So I create a file called Zeus:Config/AreaFix/1.234.56.0.LST and in it I have the echo tagnames listed one per line, like so: 

ECHO1         Example Echo #1
ECHO2         Example Echo #2
ECHO3         Example Echo #3


If the echo tagname is followed by a description (as in the above example) then it will be used to describe the area if a system asks for an %UPLINK list.

When a system (with uplink access) requests ECHO2, AreaFix scans the echolist file, finds ECHO2 and sends an AreaFix request to 1:234/56.0 asking it for the echo.

Meanwhile, the original requesting system is told that the echo has been requested from the uplink and ZMP adds a new AREA line into ZMP.cfg which sets up ECHO2 as a pass-through area. When the new echo starts flowing from the uplink, it is passed automatically to the original system and you don't need to change your configs at all!

The uplink lists are AREAS.BBS format, if your uplink can supply them. Otherwise, an edited %LIST response could be used.


The AreaFix Help Command

The following help file is sent to the user on receipt of a %HELP command in an AreaFix request - if you would like to edit it for your own needs, it is stored in Zeus:Config/AreaFix/AreaFix.hlp


1. What is an AreaFix?

Running an AreaFix saves the SysOp of a node from the annoying business
of adding/removing systems to/from their echomail distribution list.


2. Formatting your AreaFix request

Requests are made via netmail messages which contain specific
information in some of the fields. In particular, the addressee is
always 'AreaFix' and the subject is the password assigned to you by the
SysOp of this system.

For example:

From: Jon Dough (1:234/56.7)
To: AreaFix (1:234/56.0)
Subject: Password

The text of the message contains one or more request commands (one per
line) which are detailed below.


3. Information requests

You can request information from AreaFix about what echos you have
access to and which ones are already being exported to you.

These are the currently supported commands: 

      %HELP      Sends this file to your system as a netmail.

      %LIST      Lists all the echomail and file areas currently available
                 from this system.  The list also shows which areas you are
                 currently linked into.

      %QUERY     Lists all the areas you are currently linked into.

      %UNLINKED  Lists all the areas you are _not_ currently linked into but
                 are available to you.

      %UPLINK    Lists all the echomail areas available to you from this
                 systems uplinks (if any).



4. Linking and Unlinking to areas

You can link into an echo by specifying it's tagname in your AreaFix
request.

For example:

ECHONAME

Will link you into the echo with a tagname of 'ECHONAME'. If the echo
doesn't exist at this system, and you have the relevent access, the
request will be passed to this systems uplink.

You can unlink from an echo by specifying a '-' before the tagname.

For example:

-ECHONAME

As an extension to this, you can request to be linked/unlinked to/from
all the available echomail areas at this system.

%ALL
%-ALL

The first command would link your system into all the echos available to
you and the second unlinks them all. These commands do not apply to file
echos.

After any echomail link changes, AreaFix will send you a message with
the results of the request.


5. %PAUSE and %RESUME

If you wish to temporarily disable the flow of all echomail areas
without actually linking out of them, then send the %PAUSE command.

When you want to enable the echomail flow send a %RESUME command.

Netmails for your system are unaffected by these commands.

Messages in echomails areas addressed to you are also unaffected by
these commands if you are listed in the SysOp's 'Netmail remapper.'
Ask the SysOp to be listed if you wish to ensure that you receive
personal mail.


6. Rescanning

Sending a %RESCAN command to AreaFix will cause it to export all the
messages you haven't seen yet from all the echos you are linked into.

You can rescan a single area by using:

%RESCAN <Echo Name>

... which will also link you into that area if you are not already.

Specifying ALL for the echoname will have the same effect as having
no arguments.

If the BBS holds a large number of messages, you could easily get far
more than you originally intended. To get around this, you can specify
a maximum number of messages to rescan:

%RESCAN <Echo Name> <Number of Msgs>

e.g

%RESCAN WORKBENCH 100

A %RESCAN will only send you messages you have not already seen. In
order to also receive messages that have /already/ been exported to
your address, you can use the %FORCERESCAN command. This operates in
the same way as %RESCAN.


7. Remote maintainance

If the SysOp of this system has granted you full AreaFix control then
you have access to the following commands. 

      &ECHONAME               Create a new echo with the tag name
                              'ECHONAME'.  Your system will not be linked
                              into the new echo.

      ~ECHONAME               Delete the echo with a tag name of 'ECHONAME'

      # OLD_NAME : NEW_NAME   Change an echo's tagname from 'OLD_NAME' to
                              'NEW_NAME'.  The spaces are optional.

      %FROM: 1:234/56.0       Specify that the request comes from
                              1:234/56.0 instead of your system.  Note that
                              the password in the subject line must be
                              correct for your system.



Using AreaFix

AreaFix can be thought of as a robot, waiting on your system for requests from users. Each network has its own AreaFix robot. If a user wanted to receive a list of echoes which you carry in the FidoNet network, for example, they would send a netmail to the `user' "AreaFix" at your FidoNet address. In this message, they must put the command "%LIST". The AreaFix is password protected however, to ensure that nobody else attaches them to any areas they don't want (imagine suddenly one day receiving several megabytes of mail when normally you'd only get a few kilobytes - this is the abuse that passwords are designed to stop). The users password must be in the subject line.

Using AreaFix for remote SysOping

If you are away from your BBS computer, but can stay in touch with it (using a laptop with some terminal and pointing software and a mobile phone for example), then you can still manage your mail system!

You must first make sure the point address you have set for yourself has SysOp access to AreaFix. Check the relevant section in this chapter on the SYSTEM keyword. Once done, you can perform the changes mentioned in the AreaFix help file.

This system may also be useful if your BBS is run by many Co-SysOps. A co-SysOp can be in charge of a single network's (or more, remember that SysOp access can be set per-network) management while not actually needing to be at the BBS computer.

Of particular note is the "%FROM:" keyword. If a point or other downlink of the BBS is having trouble fixing into an echo (for example), then you, as a SysOp also pointing, can send an AreaFix with that users password from your address if you specify "%FROM <their address>".



Setting up Archivers

ZMP reads the Archivers configuration file so it can pack and unpack message bundles, which are traditionally archived to save transmission time with the Mailer.

When setting up your ZMP configuration you must make sure that all the archiver entries have the correct paths to the binaries. These archivers are all available from the AmiNet. 

Archiver Name             AmiNet File

ARC                       util/arc/arc.lha
LHA & LZH                 util/arc/LhA_e138.run
LZX                       util/arc/lzx121.lha
UUENCODE                  util/arc/uuxt31.lha
ZIP                       util/arc/Unzip512x.lha,
                          util/arc/zip201x.lha
ZOO                       util/arc/zoo2-0.lzh


The Archivers configuration program can be accessed from the Message->Config->Archivers menu on the Control screen, or from the Zeus:Prefs drawer.



Each archiver has various fields to be configured:

Name - The descriptive name of the archiver. This field is the one used in your ZMP.cfg to define what archiver a particular node uses. It should not have spaces in it.

Compress - The line is expanded to make the command line used to compress one or more files into this archive type. This line takes expansion codes ~a and ~f, e.g. if we were packing a file called 00003445.pkt into a file called OUTBOUND:2.888.1.0.LHA, the compress line would be expanded to "c:LHA -2 -a a OUTBOUND:2.881.1.0.LHA 00003445.pkt".

Extract - This line is expanded to make the archiver extract one or more files from an archive. This line takes expansion codes ~a and ~f, where ~a is the archive name to extract and ~f is an optional argument to extract one or more single files. If all the files are to be extracted then the program will not use the ~f argument.

Test - This line is expanded to make the archiver test the archive. This line only takes the ~a expansion code. Zeus detects whether the file tested OK by checking the result code of the archiver. If the result code is 0 then it is assumed that the archive is not corrupted.

Recog - This line is a hex string used to detect whether an archive to extract is of this type. For example all LHA archives start with two random characters and then the string "-lh5-". We represent this with the line "** ** 2D 6C 68 35 2D", where ** compares to any single character.

Show User - This flag determines whether the archiver will be able to be viewed by an on-line user accessing the archivers configuration, for example within Phoenix. Archivers such as "UUENCODE" and "ZGATE" should not have this flag set off.



Using ZMP

Finally, once ZMP is configured, you can use the program. 

Zeus Bulletin Board System (c)1992-1999 Zeus Developments
Zeus FTN Net/EchoMail, Tick & Hatch Processor v1.2

Usage: ZMP IMPORT/S,EXPORT/S,FORCE/S,TICK/S,HATCH/S,AREA/K,
           FILE/K,DESC/K,REPLACE/K,DELETE/S,BATCH/K

   IMPORT  - Dearchive and import mail
   EXPORT  - Scan message areas and pack new messages
   TICK    - Process *.TIC files
   HATCH   - Hatch a file into a TICK echo
   BATCH   - Perform a batch file hatch

   FORCE   - Force packing of all messages

HATCH options:

   AREA    - Tick tag name to hatch file to
   FILE    - Filename of file to hatch
   DESC    - File description
   REPLACE - File to be replaced
   DELETE  - Delete original file

BATCH options:

   DELETE  - Delete batch file once done



Most of the commands are quite descriptive themselves; to import your echomail using the option "Import" in the command line, to export use "Export". Many of the option can be combined on one command line, so "ZMP Import Export" is perfectly valid and actually recommended, as it means the configuration needs to be read and saved only once.

The Hatch command (to create and export a Tick file) behaves a little differently. If you specify just "ZMP Hatch", ZMP will go into interactive mode and request from you the information it needs to build a Tick file and export it.
Alternately, you can use the "Hatch options" as shown above: in this case, you specify the options required by ZMP on the command line and ZMP does not ask for them interactively. Since these are keywords (/K), you might do this: 

ZMP Hatch Area="NEW_GAMES" File="Inbound:3D_Fighter.lzx" Desc="New 3D fighting game" Replace="" Delete


Since in this case since I'm pointing to a file in my Inbound directory, I wish to delete it. ZMP will be add the file to my file base in the area which attached to the NEW_GAMES Tick echo, so I have no need to keep it in the Inbound: directory.


The ZMP Batch command lets you specify much the same thing, except the Hatch options are fetched from a file, and there can be more than one file Hatched at a time.

The Batch file (which you specify after the Batch command, i.e. "ZMP Batch=RAM:Batches.txt") is of the format: 

Tick Area1
File1
Description1
File to Replace1
Delete1 (Y/N)
Tick Area2
File2
Description2
File to Replace2
Delete2 (Y/N)


So, each Hatch entry follows directly on from the last, and each element is placed on a new line. If any entry has no option, like the Replace option for example, leave a blank line. The Delete option is a single character, either Y for Yes or N for No.

For example, the Batch file may look like: 

NEW_GAMES
Inbound:3D_Fighter.lzx
New 3D fighting game

Y


And the command line used for ZMP would be: 

ZMP Batch=RAM:Batches.txt Delete


In this case, Delete on the ZMP command line means to delete the Batches.txt file.


In the most simplistic usage, you merely call ZMP to import and export your echo mail, and would have this in an "After session" script for ZMailer: 

ZMP Import Export


If you also receive Tick files (such as nodelists) then you should also add Tick to the options. 

ZMP Import Export Tick




ZMP's Construction of a Tick file

It may be useful for you to know how ZMP refers to and treats the file when making a Tick.

If the Tick area is passthrough: ZMP will make a copy of the file given, and place the copy in the Outbound directory. This copy in the Outbound is the file ZMP's Tick (for every downlink) refers to.
If the Tick area is a file area on the BBS: ZMP will make a copy of the file given, and place the copy in the path of the file area. This is the copy which is refered to in the Tick file.

In both cases, the original of the file is no longer required by Zeus. In the case of the non-passthrough area, ZMP should respect the MultiPaths of the file area.

ZMP keeps a file which contains statistics on what has been imported from networks. The file contains:

· The total number of items imported into that area since the area was first created.
· The number of items imported each day for the last week.
· The size of items imported each day for the last week.

The statistics can be accessed with the Bin/ZMPStat program.

Error Handling

Should something go wrong while importing or exporting mail, ZMP will attempt to rescue data and, if possible, carry on working. It will also 'bail out' safely if it cannot continue working. This is a detailed, if somewhat incomplete description of what ZMP may do in case of an error:

· An inbound mail bundle (archived) fails to extract:
ZMP will rename the bundle with a ".BAD" extension and set its file note/comment to the error which was encountered. It will then attempt to import whatever packets were extracted, dealing with any that may be corrupted as normal.

· An inbound packet is corrupted:
ZMP will import the messages contained in the packet up to the point of corruption. If the corruption is easily detectable (e.g., a mangled message header) ZMP will stop importing that packet, and rename it with a ".BAD" extension. The file comment will be set to a description of the error encountered.

· A crash occours during export, leaving packets and bundles partially filled:
ZMP will export all the messages again, on the idea that it's better to have some duplicate messages go out (which will most likely be filtered out by the downlinks) than for mail to go missing. Partially completed bundles (perhaps caused by a crash during or after archiving) may have an extension representing the archiver's normal extension. In case this is a valid bundle, Zeus will rename it (so other archiving can take place) and place a message in the log file to notify you of the presence of the 'unattached' (to a FLO, HLO, etc.) bundle - "WARNING: Unattached bundle found in Outbound; renamed to <new name>".

· An inbound packet arrives which is not addressed to any of your addresses/AKAs:
The packet is treated as corrupt; it is renamed with a ".BAD" extension and the file comment set to describe the fault.
