Chapter 9 - The Internet

Introduction

Types of InterNet account

There are currently two widely used types of InterNet account: static and dynamic. Static accounts provide you with your own IP address, domain name and multiple mail boxes. Dynamic accounts allocate a new IP address for you every time you connect to your provider, have only one mailbox and usually a 'firewall' stopping outside access to your system using Telnet, FTP and other InterNet protocols.

Zeus and the InterNet

Zeus comes with six utilities to help interface your BBS to the InterNet: 

* Zeus:Bin/System/NetStart


Telnet is a very simple InterNet protocol which sends and receives text between a host and a client, much like a normal BBS session, except the data is divided up into packets and transfered over the net instead of a normal dialup connection.

Because of this similarity, several Telnet daemons have been written which allow Amiga terminal and BBS packages to interface to Telnet by opening a faked serial.device.

Some Telnet daemons allow multiple incoming sessions by allocating a new unit number to every connection and spawning an external program such as NetStart.

Telnet daemons will normally only work well with static InterNet accounts, although so called "Dynamic DNS" services are available which will assign you a hostname which you can update immediatly with whatever IP address you have been assigned for that particular call. 

* Zeus:Bin/ZGate


ZGate converts Email into Netmail, UseNet newsgroups into Echomail and vice versa. You will need to have a working FidoNet-technology mail processor setup (preferably ZMP) although you do not need to be a member of any external network if you only wish the mail and news to appear on your BBS.

ZGate will work fine with dynamic InterNet accounts but, if you want to give your users E-Mail access or run a private/public gate, a static account is preferred. Recently, ISPs have begun offering dynamic IPs with subdomains. For the purposes of this manual, these can be considered static accounts. 

* Zeus:Rexx/AmiNetZAmiMirror.rexx


The Aminet archive is the biggest collection of non-commercial Amiga software and information in the world. It is accessable on the InterNet using FTP from several sites and is constantly being added to by the Amiga community.

ZAmiMirror is an ARexx script that downloads the latest files from the archive and uploads them to file areas on your BBS.

ZAmiMirror will work with both static and dynamic InterNet accounts. 

* ZPOP3Xfer


ZPOP3Xfer transfers messages using the POP3 Internet mailbox format from the Internet to your hard drive, ready for processing with ZGate. 

* ZSMTPXfer


ZSMTPXfer transfers messages using SMTP to and from the Internet. 

* ZNewsXfer


ZNewsXfer transfers messages with the NNTP protocol from the Internet to a file on your hard drive, ready for use with ZGate.


InterNet Configuration

This is where Zeus's Internet support is set up. Most options relate to ZGate, but can be used by other programs so please fill it in even if you use another gateway program.



User Name - If you have a "dynamic" InterNet account you must enter your mailbox name. Example If your mail address is zeusbbs@net.com then set this field to zeusbbs. If you have a static account, this field MUST contain nothing.

Address - Your InterNet address. If you have a dynamic account this will be the address of your InterNet provider. Example If your mail address is zeusbbs@net.com, you would enter net.com. If you have a "static" account, this must be the full domain assigned to you,for example: with <anything>@tkgbbs.freeserve.co.uk you would put "tkgbbs.freeserve.co.uk" without the quotes.

Organization - Your organization, if you have one, or your BBS name if you wish. If this field is left blank, it will not be used.

News Receipt - Some InterNet news systems require that new articles be submitted by Email. If your provider works like this then enter the destination e-mail address for newsgroup messages here.

Save Config - Saves the configuration. If Zeus is running, it will also be updated.

Close Gadget - Quits the program. If changes have been made and you have not saved them, a requester will appear asking if you wish to save.



Options Window



Gate Type - Sets the kind of gate you wish to run

Local - Only messages written on your BBS will be gated. Any messages comming from other systems will be bounced back informing them of the situation.

Private - Messages will only be gated if they came from your BBS or from a system listed in the 'Gate Access' list AND the user has be specified in the 'User Mapping' configuration.

Indexes - ZGate keeps an index file of information about each mail and newsgroup article that it processes. By specifying a low number into this field (minimum of 100) you will save disk space but ZGate's duplicate message detection and message linking functions will not work very well. As a guide, you should set this field to the approximate number of InterNet messages you process in one week, but if this is a low number (less than 1000 is low) it is perfectly okay to increase it. Many of ZGate's advanced features depend on this database.

Your Addr - Your FidoNet address.

Gate Addr - The FidoNet address you have given to your InterNet gate. This must also be set up in ZMP.cfg (as detailed below) or whatever FidoNet message processor you are using. Usually this is a point on your BBS, not a fake node, to simplifiy things.

Domain - Usually this should be set to 'fidonet.org'. If your ISP will send you 'subdomained' e-mails, this can be your address. Please leave as fidonet.org if you are not completely sure of the Internet or gating technology involved.

Time Zone - Your time zone.

GMT Offset - The difference in hours from GMT to your time zone.

Gate Access - If 'Gate Type' is set to Private or Public then this list becomes active. It specifies the systems that may access your gate. Entries are of the form [+ or -]zone:net/node.point : + to give access or - to deny, followed by a standard FidoNet address. You can use the wildcard character '*' for any of Zone, Net, Node or Point to allow multiple systems access without having to type all the addresses in.



Examples:

+2:441/58.72

- Allow this point access.

+2:441/58.*

- Allow all my points access.

+2:441/*.*

- Allow all the nodes and points in net 441.

+2:441/*.*

- Allow all nodes/points in net 441

-2:441/59.*

- except node 59 and all his points.


By default, no systems have access so you don't need a entry of '-*:*/*.*'.

Add: Add a new gate access entry.

Del: Deletes the currently selected access entry.

ZGate

ZGate is basically a conversion utility that sits between your current InterNet setup and your BBS mail processor. It was designed like this to give a lot of flexibility in how email and newsgroup articles are processed. For example:

The simplest use of ZGate is to convert email and articles to a form which can be imported into your BBS message areas using any FidoNet mail processor (although ZMP is preferred!). This gives read only access to the InterNet for you and your users.

ZGate can of course work the other way: taking new messages from the BBS and converting them to emails and articles ready to be sent onto the InterNet.

Because ZGate converts messages to and from FidoNet packets, you can also link your points or other node systems into the areas, thus giving them access as well.

Please note that some InterNet providers will charge you extra if you want to start gating to other systems.

From version 1.5, ZGate also includes the ability to act as a simple mailing list server. Any messages in specified Fido echoes are gated to email and sent to a list of Internet email addresses.

And finally, if you wanted to keep emails and articles in InterNet format, maybe for feeding to a local network over NNTP or SMTP, ZGate can convert the messages to FidoNet format but won't delete the original files.

ZGate keeps two index files containing information from every email and newsgroup article it processes. Because of this, it has duplicate message detection, advanced message linking abilities and the unique ability to provide UseNet with correct To: and From: fields, just like FidoNet echoes!

InterNet E-Mail to Zeus

When emails are transfered from your InterNet mail host to your system, they end up as either mailbox files or individual messages depending on what software you use.  ZGate takes either format and converts them to FidoNet netmail packets in your inbound directory ready to be imported onto your BBS.

To convert a single email message, you use the GATEMAIL option with ZGate:


CLI> ZGate GATEMAIL T:NewMsg.tmp [DELETE]




The DELETE option tells ZGate to delete the email message if it was successful in converting it.



Converting a mailbox is equally as simple: just use the MAILBOX option:



CLI> ZGate MAILBOX UUMail:zeus [DELETE]






Zeus -> InterNet E-Mail



To send an email from your BBS, you need to write a netmail with the To: field set to the receipients email address (OR *IMPORTANT* - the e-mail address sometimes will not fit in the To: field, so instead write their name in To: and write the first line of your message as "To: <address>" - you can automate this in your scriptset), and the destination FidoNet address set to the gate address you specified in the InterNet config.  When you export the message, the mail processor will create a FidoNet packet in your outbound which can then be imported by ZGate using the GATEPKT option:



CLI> ZGate GATEPKT Outbound:00000000.PKT [DELETE]




This process can (and in all honesty, must) be automated by setting up ZGate as an archiver!  If you are using ZMP then add the following entry into Prefs/Archivers:



   Name    : ZGATE
   Compress: Zeus:Bin/ZGate GATEPKT ~f
   Extract : <Leave blank>
   Recog   : <Leave blank>




In your ZMP.cfg, setup the gate SYSTEM like so:



   SYSTEM .1 N3NNNNNBY GATE -NONE- -NONE- -NONE- <Group Numbers...>




This example sets the gate address to .1, the archive netmail flag on, and the archiver type to GATE.  Now, when ZMP comes to archive some messages destined for the gate address, it automatically calls ZGate which processes the packet!



If you now let users know that you have an Internet gateway on (in this example) your address at point 1, they can then send and receive e-mail, using the same methods as other gateway programs.  Ensure they know to write the e-mail address on the first line of their message using "To: <address>".  Many FidoNet programs can take care of this themselves, since it is the standard used all over FidoNet.





Newsgroup Configuration



The InterNet configuration gives ZGate enough information to import and export email but, if you want it to process newsgroups, it needs a text config file, named Zeus:Config/ZGate.cfg, which defines the groups you want to gate and how they should be handled. ZGate.CFG also allows you to seperate Mailing Lists from your using E-Mail. The mailing lists appear on the BBS in their own area, just like a gated newsgroup.



Since newsgroup tag names are usually quite long, ZGate supports mapping between newsgroup tag names and FidoNet tag names.  ZMP will happily process tags up to sixty characters long but other mail processing software may have problems.  If you will be gating newsgroups to other systems, or using a mail processor other than ZMP, you will probably need to define a shorter FidoNet tag for all your newsgroups.



A number of newsgroups have restrictions on who may post articles to them.  Some require that all new articles be sent to a moderator as email. If the moderator thinks that the article is relevant to the newsgroup, they will post it for you.



Other newsgroups have a matching discussion group where people reply and talk about the articles in the main group.  These newsgroups use the same tag name with '.d' appended to signify a discussion group.



ZGate supports both of these restriction systems automatically once the relevant information has been entered into the ZGate.cfg file.  Here is an example of what the config looks like:



;
; An example Zeus:Config/ZGate.cfg
;

;     <InterNet Tag> <FidoNet Tag>  [Moderator/Followup]

AREA  zeus.announce  ZEUS_ANNOUNCE  zeus@pavilion.co.uk   ; Moderated
AREA  zeus.news      ZEUS_NEWS      zeus.news.d           ; Followup
AREA  zeus.news.d    ZEUS_NEWSD                           ; Normal Group


; Generic Newsgroups list

; List of newsgroups, like above AREA definitions, but in an external file in
; either 'active' format, or one group name per line. As such, no mapping of
; newsgroups to different echo names or setting different moderator/followup
; addresses.

;         <Filename>

XGROUPS   UULIB:active

; Mailing lists

; For the 'origin of list', you should put the address which his in the
; To: or Reply-To: field of the E-Mails.

; It will also match on the From: address, allowing for strange mailing
; list server configurations and also allowing you to 'filter' mails
; from specific addresses into seperate echoes even if they are not
; mailing lists.

; You can have more than one LIST entry if it is necessary to match
; several different addresses as being the same mailing list. But,
; the first LIST entry for a particular echo name will be where new
; messages from the BBS are sent to.

;    <Address>                <Our echo>      <Name subscribed with>

LIST amterm@vapor.com         TKG_ML_AMTERM   neil

; Hosted mailing lists - effectively, ZGate is a mailing list server
; like a primitive majordomo. "File" is either a file in Zeus:Config/
; or you can give a complete path.
; "Name of List" is <name>@your.bbs.com, where subscribers send messages
; to and messages come from.
; add PUBLIC to the end if you want to allow anyone to post there, if they
; know the list name/address. Recommended, as this eliminates expensive
; checking of the subscribers file, for _every_ message received for this
; list.

;    <File with List of Subscribers> <Echo to Gate to> <Name of List> [PUBLIC]

HOSTEDLIST ZGate_testlist.txt        ZGATE_TEST        zgate.test     PUBLIC
HOSTEDLIST ZGate_TKG.txt             TKG               tkg

; End of example




As the example shows, you can place comments in the config by preceding them with a semi-colon ';'.  ZGate will also ignore blank lines.



The AREA keyword describes a single newsgroup and has the template:



AREA <InterNet Tag> <FidoNet Tag> [Moderator/Followup]




InterNet Tag - The tag name of the newsgroup



FidoNet Tag  - The tag name to use in FidoNet packets



Moderator/Followup - If this argument is present, it specifies either a moderators email address to which all new articles will be posted, or a follow-up discussion newsgroup tag name.  ZGate decides which type of argument you have given by checking for a '@' character.  If it finds one, it assumes an email address.







To save adding all your newsgroups in by hand, you can use the XGROUPS keyword to specify a file which contains the groups you want ZGate to process.  The format of this file is simple:  one newsgroup tag per line like this:



   zeus.announce
   zeus.news
   zeus.news.d
   <etc. etc.>




Several external newsgroup processing utilities use a similar file format (called the "active" file, often in an assign called "uunews:") which, since ZGate doesn't change the file in any way, you can 'share' it between them.



Some utilities append other information after the newsgroup name in these files, like high and low message pointers, which makes the file look like this:



   zeus.announce 1482 1266 n
   zeus.news 8273 6350 n
   zeus.news.d 17623 8232 n
   <etc. etc.>




ZGate can still read this format since it only takes the first part of each line, stopping at any space or tab character.



The disadvantage of using the XGROUPS keyword is that no FidoNet tag mapping or moderator/followup information is present.  For the example, it is equivilent to the following AREA lines:



   AREA zeus.announce zeus.announce
   AREA zeus.news     zeus.news
   AREA zeus.news.d   zeus.news.d




So, if you want tag name mapping for all your newsgroups, you will still have to enter them all in as AREA lines.  If, however, you don't want to use tag name mapping, then you only need to use AREA lines for groups that have a moderator or follow-up newsgroup.





Mailing Lists - as a subscriber



Using LIST, any e-mail which arrives can be checked to see if it came from a mailing list you have subscribed to, and if it has, to seperate those messages into a specific EchoMail Area for either just yourself or your users.



The format is:

LIST <Address>   <Our echo>   <Name subscribed with>



Address -- The address to which e-mail for the mailing list will be sent, and also the address which tells ZGate that a certain message has arrived from a particular mailing list.

On incoming mail, this address is compared to that which is in the "To:" or "Reply-To:" line of incoming e-mail.



Echo -- The echo tag on the BBS to place the messages. If ZGate's SYSTEM line in the ZMP configuration is set to create areas, it will be auto-created on the first message processed.



Name -- This is the name you subscribed with.  It is useful to subscribe with a unique name if you have a static account, but not necessary.  The rest of the address (name@<address>) must be what is configured in the Internet preferences - you cannot, for example, run list1@hotmail.com, list2@bigfoot.com.  This is the same elsewhere in the gateway system.



Sometimes, you may find the "To:" line of mailing lists changes sometimes, depending on which server is used at the mailing list home.  This is the case with the Miami mailing lists.  To get around this, it is perfectly possible to use two near identical LIST lines:



LIST miami-announce-ml@nordicglobal.com      TKG_ML_MIAMI_ANN     neil
LIST miami-announce-ml@h1.nordicglobal.com   TKG_ML_MIAMI_ANN     neil




In this case, all out going messages are correctly addressed to "miami-announce-ml@nordicglobal.com", but incoming messages can also come from "miami-announce-ml@h1.nordicglobal.com" and correctly arrive in the MIAMI echo.





Mailing Lists - as a server



The HOSTEDLIST line in ZGate.CFG allows us to create a more powerful form of mailing list - one where we server emails out to users. In this case, a FidoNet echo is assigned an email address in our domain (you must have the ability to have multiple addresses under your domain).



For example, area ZGATE_TEST has the email address zgate.test in the example configuration - when conbined with our domain this might give zgate.test@bbs.com. Now, whenever ZGate imports an email addressed to zgate.test, it will send it to this echo. Much like with a standard LIST, but in this case we don't filter on the "To:" line of the email.



HOSTEDLIST ZGate_testlist.txt        ZGATE_TEST        zgate.test     PUBLIC
HOSTEDLIST ZGate_TKG.txt             TKG               tkg




However, we can filter on the "From:" line - in the ZGATE_TEST example, anyone can send a message to zgate.test and it will be gated. In the TKG example above, you'll notice it is missing the PUBLIC argument. This means that only the email addresses listed in the file "Zeus:Config/ZGate_TKG.txt" will be allowed to email messages into the echo.



This also works in the other direction; the more useful aspect of this. When a message is posted in ZGATE_TEST, it is sent to every email address in ZGate_testlist.txt. Similarly for the TKG echo.





Newsgroups to Zeus



When transfering newsgroup articles from the InterNet to your machine, some software will create a batch file containing all the articles (often called the "RNews" format) whereas others store them as individual files (ZNewsXfer, below, uses the batch file format).  The batch method is faster and less system intensive, but ZGate will handle both formats.



To convert a batch file you use the GATEBATCH option:



CLI> ZGate GATEBATCH T:News.batch [DELETE]




To convert a single newsgroup article, you use the GATENEWS option:



CLI> ZGate GATENEWS T:News.article [DELETE]




Some InterNet software doesn't store the article in a file but instead, 'feeds' it over stdio.  ZGate has the option POSTNEWS for this type of situation.



CLI> ZGate POSTNEWS <T:News.article

ZGate's Return Codes



ZGate sends a return code to the CLI to indicate how well the gating process went, so that you can handle any special situation in a calling CLI script.



   0  -  All went well.
  20  -  Failure loading ZGate indexes - mostly likely out of memory.




In the case of 20, you can set your script to delete the indexes to make them small enough to again fit in memory, or launch a program to analyse memory fragmentation in case the computer requires a reboot.







ZAmiMirror





What is Aminet?



Only the largest collection of Amiga software, data and information in the world!  It lives on the Internet, so, if you don't have an InterNet account, this program will not be of much use to you.



There are a wide range of files which are stored in a hierarchical directory tree by the (nice) people who administrate the Aminet.  These are available for free and, since it usually contains all the latest public domain and shareware products, it is very popular with Amiga owners.





What is an Aminet Mirror?



The Aminet exists on several systems throughout the InterNet.  These are called Mirrors since each machine has an identical copy of all the files contained on all the other Aminet mirror systems.  Since so many people access the Aminet everyday, one single system would not be able to cope.



Another advantage to having several sites is that you can connect to a system 'near' you and get faster TCP/IP responses than if you were having to drag data from the other side of the world.



Using this program, your Zeus system can become an Aminet 'mini-mirror', taking in only a few directories, or a full blown mirror, taking in every directory.  Obviously the choice comes down to storage space and how much time you actually want to spend logged into the InterNet.  If you have a 64k ISDN line linked to the InterNet 24 hours a day and a 15Gb hard drive, then you might want to go the whole hog...





How does ZAmiMirror.rexx work?



It interfaces to the InterNet using the File Transfer Protocol (FTP) client NcFTP which comes as part of the AmiTCP package, but is available from the Aminet (of course).  ZAmiMirror has not been tried with any other FTP packages as they do not have the features needed by this program.



Basically, it works like this:



 - Download a list of the new files available

 - Scan through the list, noting which files are wanted.

 - Download the files.

 - If the files have been downloaded successfully, upload them to the matching Zeus BBS file areas.





Setting up ZAmiMirror



1. This is not a simple task but by following the steps below you should not have any problems.  If you do encounter problems with the FTP side of things and are not confident with NcFTP, you should seek help from someone who is.



2. First of all you need a working InterNet setup.  If you haven't got it working properly yet then stop reading this and go sort it out!



3. Next you need to find the closest reliable Aminet mirror.  For the purposes of this document we shall use the Imperial College's site in the UK - its address is sunsite.doc.ic.ac.uk.



4. Decide where on your system you want to store your Aminet mirror.  Make a directory there called 'Aminet'.  We shall use 'DH3:' as an example.



5. Load up Zeus:Rexx/ZAmiMirror.rexx into your text editor and take a look at the user variable section.  It looks something like this:



 Base     = 'DH3:Aminet/'
 AmiAddr  = 'sunsite.doc.ic.ac.uk'
 SysAddr  = 'phoenix.doc.ic.ac.uk'
 AmiDir   = 'pub/aminet'
 MaxSize  = 1024000
 RecName  = 'ADT_RECENT_7'
 LogFile  = 'Logs:ZAmiMirror.log'
 FullTree = 'No'




6. Edit the 'Base' line to reflect where your Aminet directory is.  Don't forget the slash '/' at the end.



7. Put the address of your chosen Aminet mirror site into 'AmiAddr'.



 'SysAddr' and 'AmiDir' will be covered later...



8. Set the 'MaxSize' variable.  Files that are larger than 'MaxSize' will not be downloaded.



 RecName' is the filename of the recent files list on your chosen Aminet mirror site.  It comes in two flavours:



 ADT_RECENT_7  - New files in the past seven days
 ADT_RECENT_14 - New files in the past forteen days




9. Choose a name and location for the ZAmiMirror log file and set 'LogFile' accordingly.



10. If you want to mirror all of the Aminets directories then set 'FullTree' to 'Yes'



11. Save the script at this point.



12. Log into the InterNet and get a AmigaDOS shell ready.



13. Type 'CD DH3:Aminet' (or wherever your Aminet directory is).



14. Type 'NcFTP sunsite.doc.ic.ac.uk' (or whatever your Aminet site is).



15. When connected and the NcFTP prompt appears it should look something like this:



 phoenix.doc.ic.ac.uk:/
 ncftp>




 Although you connected to 'sunsite.doc.ic.ac.uk', the site name is actually 'phoenix.doc.ic.ac.uk' and this must be entered into the 'SysAddr' variable.



 If the site name is the same as the address in 'AmiAddr', you still need to set 'SysAddr'.



16. Type 'cd pub/aminet'



 If the prompt now looks like this:



 phoenix.doc.ic.ac.uk:/pub/aminet
 ncftp>




 Then 'AmiDir' is correct.  If the site complains that the directory does not exist then you will have to find the 'aminet' directory and set 'AmiDir' accordingly.

ZNewsXfer



Zeus Bulletin Board System (c)1992-2002 Zeus Developments
Network News Transfer Protocol for TCP/IP - Written by Nick Loman and Neil Williams

Usage: ZNewsXfer NEWSHOST/A,PORT/N,BATCHFILE,AREASFILE,SOCKETS/N,APPEND/S,
                 LASTDATE,DEBUG/S,KILLFILE/K,GROUPLIST/K,NEWGROUPS/K,TEMPDIR/K

   Upon first invocation, the LASTDATE argument must be specified in
   date format YYMMDD HHMMSS.




NEWSHOST - NNTP host to get news from, e.g. "news.demon.co.uk", "pubnews.demon.co.uk", "news.mistral.co.uk"



PORT - Port number to connect to. Defaults to NNTP's port, 119 (usually no need to change).



BATCHFILE - Output file for "RNews" formatted batch files containing messages, defaults to "Ram:Batch".



AREASFILE - "Active" file, file containing list of newsgroups, one per line. Can be shared with an NNTPd's Active file, the extra data used by NNTPd is ignored. See ZGate's XGROUP configuration item description.



SOCKETS <num> - Number of sockets/connections to open to the server, to increase performance by ensuring that while one connection waits the next is downloading something. Best results with a modem appear to be with 4 sockets - experiment with you connection to find the best performance. Defaults to 1.



APPEND - Append instead of overwriting BATCHFILE.



LASTDATE <date> - Specify the oldest news messages to retreive in YYMMDD HHMMSS format, if not specified uses a "Zeus:Config/LastNNTP_<servername>" file for data, e.g. "030116 000000" (include quotes). Only specify the data on the first invocation; afterwards ZNewsXfer collects messages from the date it has stored through to the present.



KILLFILE <file> - Name of kill file. A kill file contains one or more patterns to match and kill on Message-IDs you do not wish to receive.



GROUPLIST <file> - Retrieve entire group listing from server into <file>. Use sparingly - these lists are massive.



NEWGROUPS <file> - Retrieve all new groups since LASTDATE from server into <file>. This allows you to use GROUPLIST once, then use NEWGROUPS to keep it up to date with new additions at the server.



TEMPDIR <file> - Where to store temporary files. Defaults to T:.





Example Lines



1> ZNewsXfer news.mistral.co.uk PORT 119 BATCHFILE uunews:batch

      AREASFILE Zeus:Config/Msg/NewsGroups.Txt SOCKETS 4 APPEND

      LASTDATE "951117 000000"  TEMPDIR "ram:"



1> ZNewsXfer news.mistral.co.uk SOCKETS 2



1> ZNewsXfer news.freeserve.co.uk BatchFile Mail:BatchFile

      AreasFile uunews:active Append

      Newgroups Zeus:Config/NewNewsGroups.txt

      KillFile Zeus:Config/NewsKillFile Sockets 4

2> ZGate GateBatch Mail:BatchFile DELETE
